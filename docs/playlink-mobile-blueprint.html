Définition · Architecture · Prototype

Playlink en application mobile, jouable sans réseau

Porter les 8 jeux de Playlink sur iOS et Android en Flutter, 100 % offline façon Candy Crush, avec un back-office neuf et léger pour le contenu et les stats.

Flutter · iOS + Android Next.js back-office sur Vercel Neon Postgres + Clerk Budget infra < 20 $/mois Cible 100–5 000 utilisateurs
00

Vision & périmètre de la V1

Playlink devient une application mobile native-like en Flutter, distribuée sur l'App Store et le Google Play Store. L'app fonctionne entièrement hors-ligne : on télécharge le jeu une fois, et plus jamais besoin de réseau pour jouer. Le réseau ne sert qu'à trois choses secondaires : récupérer les mises à jour de contenu (~1×/mois), synchroniser le compte optionnel d'un joueur, et remonter des statistiques anonymes.

Le modèle de jeu ne change pas : pass-and-play sur un seul téléphone. Plusieurs joueurs autour d'un appareil, on se le passe, les scores se cumulent entre les parties. Pas de multi-appareils, pas de temps réel.

Dans la V1

  • Les 8 jeux du catalogue actuel portés à l'identique (Action ou Vérité, Icebreaker, Dégât Débat, Qui de nous, Mime, Thé ou café, Dilemme, Devine le mot)
  • Sélection catégorie → réglage d'intensité (1–5) → deck de 10 cartes tirées au poids de l'intensité → swipe → vote → résultats
  • Profils joueurs locaux, utilisables sans aucun compte
  • Compte optionnel (Clerk) qui débloque : leaderboard entre les profils du compte, badges persistants, sauvegarde cloud
  • Statistiques joueur persistantes en local (badges, historique, progression par tag)
  • Création de cartes personnalisées — rattachées au compte de leur auteur, privées jusqu'à publication éventuelle par toi au back-office, respectant le format d'un jeu précis
  • Like d'une carte (nécessite un compte, remonte dans l'espace perso + au back-office)
  • Partage d'une carte : image générée avec le branding Playlink + lien vers le store
  • Multilingue FR + EN — interface et contenu ; cartes non traduites affichées en français
  • Notifications push, feedback haptique, animations soignées, mode sombre
  • Back-office neuf : CRUD contenu, vue des cartes personnalisées avec publication au catalogue, dashboard stats (batch horaire), export des cartes non traduites

Explicitement hors V1 (mais l'architecture le prévoit)

  • Tout paiement — l'app reste gratuite pour recueillir des retours
  • Le paywall freemium par abonnement (semaine / mois / année), par catégorie ou intensité
  • Multi-appareils, parties en réseau, classement mondial
  • Catalogue public de cartes communautaires
  • Récupération des joueurs / utilisateurs de l'app web actuelle
Principe directeur

Chaque décision est prise pour minimiser le coût de maintenance : services managés à généreux free tier, pas d'infra à babysitter, logique métier dans l'app (pas de serveur de jeu), back-office qui ne fait que du CRUD et de la lecture de stats.

01

Ce que révèle l'audit du code actuel

J'ai lu le monorepo playlink-v2. Trois constats déterminants pour la faisabilité offline.

1 — Aucune mécanique serveur en temps réel

Le serveur ne fait qu'une chose pour le jeu : GET /api/cards/export renvoie tous les jeux → catégories → cartes actives en un seul JSON, avec un Cache-Control: max-age=300. Tout le reste est de la logique cliente pure, déjà écrite en TypeScript et directement transposable en Dart :

  • Tirage du deck — shuffle() (Fisher-Yates) puis pickWeighted() qui pondère les cartes selon l'intensité cible du jeu, coupe à 10 cartes. Aucun appel réseau.
  • Scores & votes — sessionStore (Zustand + sessionStorage) : assignPoint, skipCard, nextPlayer, cumul des tagScores par joueur. Pur état local.
  • Types de joueur — tag-mapping.ts : 14 tags canoniques, une table de normalisation (ami → amitié…), getPlayerType() qui déduit un archétype (« Le Clown de service », « L'Énigmatique »…) du profil de tags. Constante, embarquable.
Conclusion

Le 100 % offline est réaliste sans compromis. La seule chose à « déserveuriser » est l'attribution des badges (voir ci-dessous).

2 — Les badges sont à moitié serveur, à rendre 100 % local

Aujourd'hui, POST /api/sessions appelle checkAndAwardBadges() : la règle d'attribution (« totalScore ≥ 20 → badge party_legend ») vit dans le code serveur, sur des agrégats Prisma. Les 5 badges actuels sont hardcodés dans la route.

En mobile, cette logique doit tourner sur l'appareil à la fin de chaque partie, sur la base SQLite locale. Le back-office ne définit que les métadonnées d'un badge (clé, nom, icône, description) ; la règle reste une fonction Dart identifiée par la clé du badge.

3 — Le modèle joueur : compte → profils, tags sur les profils

Le schéma actuel (AppUser → Player[] → GameSession / GameSessionPlayer) confirme ta description :

  • Un compte gère plusieurs profils jouables (comme les joueurs d'une session)
  • Les badges sont rattachés au compte
  • Les tagScores (l'archétype) sont rattachés au profil
  • Le leaderboard est where: { appUserId } — un classement des profils que tu as toi-même enregistrés, pas un classement mondial

En mobile : les profils vivent en local (SQLite), utilisables sans compte. À la création d'un compte, on merge le local vers le cloud (profils + historique + tagScores + badges déjà débloqués). Le leaderboard « entre potes » se recalcule alors côté serveur, et reste consultable hors-ligne car il est aussi calculable en local (toutes les données sont sur l'appareil).

Logique de jeu — déjà cliente, à porter en Dart

  • lib/intensity-deck.ts — intensityWeight(cardIntensity, target) = 1 / (1 + |écart|)^k avec k = INTENSITY_WEIGHT_EXPONENT (1.5). Aucune carte n'a un poids nul. pickWeighted(cards, target, count) = tirage pondéré sans remise : favorise les cartes proches de l'intensité visée sans jamais exclure les autres. Le deck n'est jamais vide.
  • gameStore.startDeck() — pickWeighted(shuffle(category.cards), intensitéDuJeu, cardsPerGame). shuffle = Fisher-Yates. cardsPerGame défaut 10.
  • Cycle de session (sessionStore) — phases idle → setup → playing → voting → results. assignPoint(playerId, tags) incrémente le score + cumule les tags, passe en voting. skipCard enregistre le résultat sans point. nextPlayer = (index + 1) % players.length. Scores cumulés entre parties — resetSession conserve players, scores, tagScoresGained.
  • lib/tag-mapping.ts — 14 tags canoniques (amitié, humour, vérité, action, stratégie, créativité, courage, mystère, flirt, tabou, société, ambition, famille, nostalgie). Table TAG_MAP normalise ~150 tags bruts. getPlayerType(tagScores) → archétype (« Le Clown de service », « L'Énigmatique », « Le Séducteur »…) selon le tag dominant du profil.
Aucune de ces fonctions n'appelle le réseau

Elles sont pures et déterministes (au Math.random près). Le portage Dart est mécanique et testable ligne à ligne contre l'implémentation TS.

Mécaniques à confirmer pour le portage

Tes descriptions produit de chaque jeu (message du 5 septembre) donnent l'intention éditoriale. Deux jeux ont une mécanique qui dépasse le simple swipe de carte actuel et méritent une vérification de comportement en phase 2 :

  • Qui de nous — « le groupe désigne, la majorité tranche » : implique un vote collectif sur un joueur désigné, pas un vote binaire oui/non sur une seule personne comme le VoteScreen actuel. À concevoir comme un écran de désignation multi-joueurs.
  • Thé ou café — mécanique de duel binaire itératif (« thé ou café ? » jusqu'à converger vers le mot) : différente du mime classique, se rapproche d'un jeu de 20 questions à choix binaire forcé. Nouveau composant à concevoir, pas un portage direct de PlayCard.
  • Devine le mot — mécanique « 3 indices maximum » avec pénalité si un indice est mal choisi : nécessite un compteur d'indices et une logique de fin de tour anticipée, absente du flux swipe actuel.
  • Mime, Action ou Vérité, Icebreaker, Dégât Débat, Dilemme — mécanique de swipe/carte inchangée, portage direct.

Better Auth — alternative documentée

Better Auth est une lib open-source : les tables d'auth vivent dans ta base Neon, zéro dépendance SaaS, gratuit pour toujours. Le coût : tu écris et maintiens toi-même la vérification d'email, le reset de mot de passe, la rotation des tokens, et l'intégration Sign in with Apple / Google. À reconsidérer si Clerk devient payant à ton échelle (peu probable avant > 10 000 utilisateurs actifs/mois) ou si tu veux tout rapatrier. La bascule Clerk → Better Auth touche l'écran de login de l'app et l'endpoint /sync, pas le reste.

Le problème Supabase — et pourquoi Neon

Tu as bien identifié le risque. Sur le plan gratuit Supabase, un projet est mis en pause après 7 jours sans activité, et le réveil prend 1 à 2 minutes. Pour une app dont le premier lancement doit être instantané, c'est rédhibitoire. Et le cron-qui-ping est un antipattern : fragile, et détectable comme activité artificielle.

Neon résout ça :

  • Neon scale-to-zero aussi après ~5 min d'inactivité — mais le réveil est ~500 ms, invisible. Pas de « mise en pause » du projet : la base reste toujours joignable.
  • Intégration Vercel native : vercel integration add neon, la DATABASE_URL est injectée automatiquement. Branch DB par preview deploy incluse.
  • Free tier : 0,5 GB de stockage (ta base utile ≈ 5 MB), largement au-dessus de 5 000 utilisateurs.
  • Aucun cron de keep-alive à maintenir.
Effet de bord favorable sur ton quota

Avec Neon + Clerk, tu n'ajoutes aucune base Supabase. Tes 2 slots Supabase restent entièrement pour l'app web actuelle. Une adresse mail dédiée au projet (alias type playlink@…) reste recommandée pour rattacher Apple Developer, Google Play, Neon, Clerk, PostHog, GitHub — sans tout accrocher à ton compte perso. Non bloquant, mais à faire tôt.

05

Offline & synchronisation

L'app est offline-first strict : toute action réussit immédiatement en local, la synchro est un effet de bord opportuniste. On ne bloque jamais l'utilisateur sur le réseau.

La file de synchronisation

Toute opération qui doit remonter au cloud est écrite dans sync_queue avec un type et un payload. Un worker se déclenche quand : l'app passe au premier plan, la connectivité revient, ou toutes les 15 min en tâche de fond. Il envoie les items par lot à POST /sync, marque syncedAt, réessaie avec backoff.

session.completedFin de partieOui (sinon reste local)
badge.earnedBadge débloquéOui

Le merge local → cloud (création de compte)

  1. L'utilisateur jouait sans compte : profils, parties, badges, likes sont en SQLite avec des uuid locaux.
  2. Il crée un compte via Clerk. L'app envoie un seul payload account.merge : liste des profils (avec leur localId), historique complet des sessions (chaque session porte un clientSessionId stable), badges débloqués, likes.
  3. Le serveur crée les Profile, SyncedSession (dédupliqués sur clientSessionId), EarnedBadge, CardLike (ignorés si le couple existe déjà). Il renvoie la table de correspondance localId → remoteId.
  4. L'app écrit les remoteId dans local_players. À partir de là, chaque nouvelle partie est poussée en incrémental.

Le merge est idempotent : rejouer le même payload ne crée pas de doublons. Utile si l'utilisateur se reconnecte sur un autre appareil — on récupère alors le cloud vers le local (sens inverse, même logique de correspondance).

Publication d'une carte personnalisée au catalogue officiel

Une carte perso créée avec un compte (workflow C1) remonte au back-office via custom_card.created. Elle reste privée — invisible des autres utilisateurs dans l'app — jusqu'à ce que toi, depuis le back-office, tu bascules le toggle « Publier au catalogue » (§08).

  1. Le toggle crée une nouvelle Card officielle dans le jeu/catégorie/intensité d'origine, avec le texte figé au moment de la publication et un champ sourceCustomCardId (traçabilité vers l'auteur).
  2. La CustomCard d'origine continue d'exister et de vivre indépendamment : l'auteur peut l'éditer ou la supprimer sans jamais toucher à la version publiée. Ce n'est pas une référence live, c'est une copie.
  3. Si l'auteur modifie sa carte après publication, la Card officielle ne bouge pas automatiquement. Le back-office peut simplement signaler (via updatedAt local > date de publication) que la source a changé — c'est toi qui décides de republier ou non.
  4. La Card publiée entre dans le ContentRelease suivant comme n'importe quelle autre carte du catalogue (§06).

Le leaderboard hors-ligne

Le classement « entre mes profils » se calcule toujours en local à partir de player_totals (score cumulé + parties, par profil). Le cloud ne sert qu'à répliquer ces données vers un second appareil. Pas de dépendance réseau à l'affichage.

Triche sur les scores — accepté en V1

Un score fait hors-ligne est déclaratif : l'app pourrait mentir au serveur. Comme le leaderboard est privé au compte (tu classes tes propres potes), l'enjeu est nul. Pas de validation serveur en V1. Si un classement public arrive un jour, il faudra une validation côté serveur — l'architecture ne l'empêche pas.

06

Distribution du contenu

Modèle retenu : hybride embarqué + OTA

Vu tes volumes réels — ~1 600 cartes = ~2 à 4 MB de JSON une fois sans le bruit SQL, et ~100 GIF = 30 MB — et un rythme de changement de 1×/mois, le bon compromis est :

  1. Snapshot embarqué dans le binaire — un content_v{n}.json + tous les GIF sont livrés dans l'app. Au tout premier lancement, l'app seed SQLite depuis ce fichier. Zéro réseau, jeu immédiat. Poids app estimé : ~45–60 MB, comparable à n'importe quel jeu casual.
  2. Check de version au lancement (si réseau) — GET /content/latest renvoie { version, snapshotUrl, changelog }. Si version > content_meta.version, l'app télécharge le snapshot en tâche de fond, puis remplace le contenu SQLite d'un bloc à la prochaine ouverture. Les GIF nouveaux/modifiés sont téléchargés à la demande et mis en cache (identifiés par hash).
  3. Publication depuis le back-office — un bouton « Publier une version » fige l'état courant du contenu dans un ContentRelease, génère le snapshot JSON, l'upload sur Vercel Blob, incrémente version. Rien n'est servi aux apps tant qu'on n'a pas publié — on édite tranquillement.

Pourquoi ce modèle plutôt que les autres

  • Pas « tout dans le binaire, MAJ par les stores » : une coquille dans une carte t'obligerait à une revue App Store de 1–3 jours. Inacceptable.
  • Pas « tout téléchargé au 1er lancement » : premier lancement sans réseau = app vide. Mauvaise première impression, et tu vises justement des retours de testeurs.
  • L'hybride : joue tout de suite, se met à jour en silence, et une correction de contenu est en ligne en minutes sans passer par Apple. À 1×/mois, le trafic de MAJ est négligeable (~4 MB par appareil par mois).
07

Migration depuis la base Playlink actuelle

On migre uniquement le contenu : jeux, catégories, cartes, règles + slides, badges. Pas les User, AppUser, Player, GameSession, Event, AuditLog.

Procédure

  1. Dump ciblé depuis la Supabase actuelle (URL de connexion directe, port 5432) : 
    pg_dump --data-only --table=games --table=game_rules \
  --table=game_rule_slides --table=categories \
  --table=cards --table=badges \
  "$DATABASE_URL_DIRECT" > playlink_content.sql
  2. Script de transformation (Node, dans le nouveau repo, scripts/migrate-content.ts) : lit le dump, mappe vers le nouveau schéma Prisma. Transformations connues :
    • Card.difficulty (easy|medium|hard, legacy) est déjà remplacé par Card.intensity (1–5) dans le schéma actuel — on prend intensity tel quel.
    • Card.tags[] : on conserve les tags bruts et on pré-calcule les tags canoniques via un portage de tag-mapping.ts, stockés à part pour les archétypes.
    • Chaque Card, Category, Game, Badge reçoit originalLocale = "fr" et aucune *Translation (à produire ensuite).
    • Les id cuid actuels sont conservés — ça simplifie tout futur re-import et garde les GIF référencés.
  3. Images (GIF) : les 100 assets sont aujourd'hui référencés par URL dans GameRuleSlide.imageUrl (et éventuellement dans le texte des cartes). Script scripts/fetch-assets.ts : télécharge chaque asset, le renomme {hash}.gif, remplit la table assets, réécrit les références en asset://{ref}. Les fichiers vont dans apps/mobile/assets/content/ (embarqués) et sur Vercel Blob (OTA).
  4. Import dans Neon via prisma db seed pointant sur le script. Jamais prisma migrate dev sur une base contenant des données (même règle que le repo actuel).
  5. Vérification : script scripts/verify-migration.ts qui compte lignes source vs cible par table et liste les écarts — 8 jeux, 28 catégories, et le total exact de cartes actives calculé depuis l'export réel (§02), pas estimé.
  6. Première ContentRelease version 1 générée → snapshot embarqué dans le premier build de l'app.
Accès dont j'aurai besoin

Pour écrire les scripts de migration : le schema.prisma actuel (je l'ai déjà lu), et soit un dump de la base soit un accès lecture à la Supabase de prod (URL directe port 5432). Les GIF : soit leur URL de base, soit un dossier. Rien de tout ça n'est nécessaire pour valider ce document — c'est pour la phase d'implémentation.

09

Freemium — préparé, pas construit

Rien de payant en V1. Mais on ne se ferme aucune porte. Ce qu'on prévoit dès maintenant, sans le développer :

  • Modèle : abonnement (semaine / mois / année), pas d'achat définitif. La restauration d'achat et la vérification de reçu suivront la logique subscription des stores.
  • Découpage du contenu : chaque Category et chaque niveau d'intensity porte déjà un champ tier (free par défaut). Le paywall se branchera dessus sans migration.
  • Entitlements : prévoir RevenueCat (free tier jusqu'à ~2 500 $ de revenu mensuel) — il gère iOS + Android, la restauration, les reçus, le statut d'abonnement cross-plateforme. L'app lit un booléen isPremium ; RevenueCat fait le sale boulot.
  • Compte requis pour payer : l'abonnement se rattache au compte store et se reflète dans Account.premiumUntil côté Neon (via webhook RevenueCat), pour que le statut suive l'utilisateur d'un appareil à l'autre.
  • UX : quand l'app est gratuite, aucun élément de paywall visible. Le jour venu, une catégorie tier: premium affiche un cadenas + une modale d'abonnement — même pattern que la modale « créer un compte » actuelle.
Coût de la préparation aujourd'hui

Trois champs en base (tier, premiumUntil) et une abstraction EntitlementService dans l'app qui renvoie toujours true en V1. C'est tout.

10

Direction visuelle — l'ambiance « Netflix »

Pas une refonte de structure : la home reste une grille de jeux, pas des rangées éditoriales. Ce qu'on emprunte à Netflix, c'est un langage visuel — fond sombre immersif en base, les couleurs de chaque jeu comme accents vifs dessus, du mouvement qui donne du poids aux transitions. Trois principes, applicables à toute l'app.

Référence visuelle externe

Un wireframe de l'app a été esquissé avec Claude Design : Application mobile Playlink. À utiliser comme point de départ visuel pour la phase 2 — à vérifier/aligner avec le catalogue de jeux réel (§02) et les principes ci-dessous au moment de sa reprise en Flutter, plutôt qu'à considérer comme figé.

1 — Fond sombre en base, partout

L'app n'a plus de mode clair par défaut : le sombre devient le socle (quasi-noir, pas gris neutre — un noir légèrement teinté vers l'indigo pour rester chaleureux). Le F2 actuel (« Clair / sombre / système ») garde un mode clair en option pour l'accessibilité, mais l'app est designée sombre-first, sombre par défaut au premier lancement.

  • Home — fond quasi-noir ; chaque tuile de jeu garde son colorMain/colorSecondary mais en dégradé contenu à la tuile, pas en fond d'écran plein — exactement comme une affiche colorée qui se détache d'un fond de catalogue sombre.
  • Écran de jeu — ne change pas : le dégradé plein écran colorMain → colorSecondary reste, il est déjà l'accent immersif propre à chaque jeu (Icebreaker bleu, Action ou Vérité rose…). Le sombre encadre cette expérience sans jamais la concurrencer.
  • Profil / réglages / classement — fond sombre uniforme, cartes en surface légèrement plus claire (élévation), textes clairs. Mêmes tokens partout, pas de re-décision écran par écran.

2 — Scale + glow au focus et au tap

Toute tuile interactive (jeu, catégorie, carte du profil) répond au toucher par un scale ~1.04–1.06 plus une ombre portée colorée (glow) reprenant la couleur du jeu — pas une simple opacité ou un aplat gris comme l'état pressé actuel. L'effet doit se sentir « premium » sans ralentir l'interaction : durée courte (~120–160 ms), easing avec un léger dépassement (spring, pas linéaire).

  • Tap — scale down léger (0.97) à l'appui, puis rebond au relâchement
  • Sélection prolongée (ex. tuile qui reste en avant pendant un choix) — scale up (1.05) + glow qui pulse doucement, prefers-reduced-motion respecté (glow statique, pas de pulse)

3 — Transitions cinématiques entre écrans

Le passage home → jeu ne doit plus être un simple push de route : la tuile tapée s'étend et devient l'écran suivant (shared element transition), comme ouvrir une fiche Netflix depuis son affiche. En Flutter : Hero widget sur la tuile de jeu, avec une animation de morph vers le header de l'écran de catégories (même couleur, même icône, qui se repositionnent en douceur).

  • Home → jeu : la tuile s'agrandit en plein écran, son dégradé de couleur devient le fond de l'écran de sélection de catégorie
  • Retour : l'animation inverse, symétrique — jamais un aller sans un retour cohérent
  • Portée : réservé aux transitions à fort enjeu émotionnel (entrer dans un jeu, ouvrir les résultats de fin de partie). Pas sur chaque micro-navigation — un `Hero` sur tout casserait le rythme et coûterait en fluidité sur les appareils bas de gamme.
Ce que ça change dans le plan de prototype

La palette sombre et les tokens de couleur sont posés dès la phase 2 (coquille de l'app) — c'est plus coûteux à retrofitter après coup qu'à poser dès le départ. Le Hero transition home→jeu et le glow sur tap s'ajoutent en même temps que les animations de carte (référence Undercover by Bluff, déjà prévue phase 2).

Liste des workflows de l'app

Tous jouables hors-ligne sauf mention réseau. Chaque workflow = un parcours utilisateur complet à implémenter et à tester.

A · Démarrage & contenu

A1

Premier lancement

Splash animé → seed de SQLite depuis le snapshot embarqué → choix de langue (détectée, modifiable) → onboarding 3 écrans (comment on joue, le compte optionnel, consentement analytics) → ajout des joueurs de la session → home.

A2

Lancements suivants

Splash court → écran des joueurs de la session (la liste persistée depuis la dernière fois, modifiable) → home. En parallèle et silencieusement : réseau check de version de contenu, worker de sync, refresh des entitlements.

A3

Mise à jour de contenu

réseau Nouvelle version détectée → download en fond → bandeau discret « nouveau contenu, redémarre pour l'appliquer » → swap au prochain démarrage → content_updated.

B · Jouer une partie (cœur)

B1

Choisir un jeu

Home = grille des 8 jeux (icône, couleurs, nom) + CTA qui ouvre une modale listant les joueurs de la session (modifiable à tout moment, sans quitter la home). Tap sur un jeu → page du jeu avec ses catégories + accès aux règles (modale slides).

B2

Configurer la partie

Choix de catégorie → aperçu d'une carte aléatoire → réglage d'intensité 1–5 (mémorisé par jeu) → réglage cartes/partie (défaut 10). Les joueurs ne sont pas redemandés ici — c'est la liste de session déjà en place (A1/A2/B1) qui joue.

B3

Joueur actif — en attente

« C'est à ton tour ! » + avatar et nom du joueur actif + bouton « Voir la carte ». La carte du deck n'est pas encore affichée.

B4

Carte révélée

Tap « Voir la carte » (haptique) → « C'est au tour de {joueur} » + carte du deck affichée + CTA « Voter ». Le compteur i / n n'avance pas encore — voir la carte ne la « consomme » pas.

B5

Vote

Tap « Voter » → le CTA se transforme en « Est-ce que {joueur} mérite un point ? » + boutons Oui / Non. Le vote est obligatoire pour avancer : c'est au moment du Oui/Non que le currentIndex incrémente et que assignPoint/skipCard s'exécutent. Puis écran « passe le téléphone » si > 1 joueur → retour à B3 pour le joueur suivant, jusqu'à la fin du deck.

B6

Résultats

Deck épuisé. Si un badge est débloqué : modale animée « Félicitations ! Tu as débloqué le badge {x} », dismissible, avant l'écran de résultats. Puis classement de la partie + archétype de chaque joueur + CTA « Rejouer » / « Retour à l'accueil » / « Partager » (score final — sans compte requis). Écriture de game_sessions + session_players + player_totals. Enqueue sync si compte.

B7

Rejouer / changer

« Rejouer » → écran de choix de catégorie du même jeu (B2), même liste de joueurs. « Retour à l'accueil » → home. Les scores restent cumulés entre parties (reset explicite uniquement).

C1

Créer une carte

Depuis la page profil (compte requis) → « Mes cartes » → liste des cartes créées par l'utilisateur + CTA « Créer une carte » → formulaire (jeu, catégorie, texte, toggle « actif ») → validation → carte ajoutée à la liste + confirmation. custom_card_created.

C2

Jouer avec ses cartes

Une carte perso avec le toggle actif entre automatiquement dans le pool de tirage de sa catégorie. Le toggle sert à activer/désactiver une carte donnée sans la supprimer — pas de réglage global à la config de partie.

C3

Gérer ses cartes

Depuis « Mes cartes » : éditer le texte, activer/désactiver, supprimer. Rattachées au compte (pas au profil joueur ni à l'appareil) — nécessite une connexion. Jamais visibles par un autre utilisateur dans l'app.

Publication au catalogue officiel

réseau Toute carte perso créée avec un compte remonte au back-office (visible avec son auteur). Toi seul, depuis le back-office, tu bascules un toggle « Publier au catalogue ». Voir §08 pour le mécanisme (copie figée, pas de référence live).

D1

Jouer sans compte

Tout le jeu, les cartes perso, l'historique, les badges fonctionnent en local. Un bandeau discret suggère le compte pour « sauvegarder et voir le classement ».

D2

réseau Modale déclenchée par une feature verrouillée (leaderboard, like). Clerk : Apple / Google / email+mdp / magic link. À la 1re connexion → merge local → cloud (workflow §05).

D3

Multi-appareils

D6

Déconnexion garde les données locales. Suppression de compte (RGPD) : efface le cloud, propose de garder ou effacer le local.

  • Réglages F1–F2
  • Livrable : app complète sans compte, avec progression persistante

Phase 4 — Compte & synchronisation

  • Clerk dans l'app (Apple / Google / email / magic link)
  • sync_queue + worker + endpoint POST /sync côté back-office
  • Merge local → cloud idempotent (D2), pull cloud → local (D5)
  • Suppression de compte RGPD (D6)
  • Livrable : un joueur peut sauvegarder et retrouver sa progression sur un autre appareil

Phase 5 — Communauté & analytics

  • Like (E1) + génération d'image de partage et deep link store (E2)
  • Formulaire « Mes cartes » (C1–C3) + vue back-office des cartes utilisateur + toggle de publication (C4)
  • PostHog : instrumentation de tous les événements + écran de consentement
  • Cron horaire d'agrégation + dashboard stats + vue traductions manquantes
  • Livrable : back-office de suivi opérationnel, boucle de feedback communautaire fermée

Phase 6 — Polish & mise en magasin

  • Notifications push (F3), OTA de contenu de bout en bout (A3), états hors-ligne (F5)
  • EntitlementService qui renvoie true + champs tier en base (préparation freemium, §09)
  • Icônes, splash, captures stores, fiches App Store / Play (FR + EN), politique de confidentialité
  • TestFlight + piste de test fermée Google Play
  • Livrable : build soumis aux deux stores
Pas de deadline — mais un ordre à respecter

Les phases 1 et 2 sont indépendantes et peuvent avancer en parallèle. Les phases 3→6 sont séquentielles. Chaque phase est une PR (ou un lot de PR) revue avant de passer à la suivante.

# Playlink Mobile — Instructions Claude

## Objectif
App mobile Flutter (iOS + Android) des 8 jeux Playlink, jouable 100% hors-ligne.
Back-office Next.js pour le contenu et les stats. Doc de référence complète :
`docs/playlink-mobile-blueprint.html`.

## Monorepo
- `apps/mobile`      — Flutter, Dart 3. drift (SQLite), Riverpod, go_router.
- `apps/backoffice`  — Next.js 15 App Router, Prisma, shadcn/ui. Déployé sur Vercel.
- `packages/content-schema` — types partagés du snapshot de contenu (Zod + génération Dart).
- `scripts/`         — migration du contenu depuis l'ancienne base Playlink.

## Règles absolues — Base de données
- Base cloud : **Neon Postgres** via Vercel Marketplace. JAMAIS Supabase ici.
- JAMAIS `prisma migrate dev` sur une base avec des données → utiliser `prisma migrate deploy`.
- `prisma migrate dev --create-only` pour créer une migration sans l'appliquer.

## Règles absolues — Offline-first
- Toute action utilisateur réussit d'abord en local (SQLite). Le réseau est opportuniste.
- Aucun écran d'erreur réseau bloquant. Features réseau → état "se synchronisera plus tard".
- La logique de jeu (deck, scores, badges, archétypes) vit dans l'app, jamais sur le serveur.
- Le back-office ne fait que du CRUD et de la lecture d'agrégats. Pas de serveur de jeu.

## Auth
- Joueurs : **Clerk** (Apple / Google / email+mdp / magic link). Alternative documentée : Better Auth.
- Éditeurs back-office : distincts des joueurs (table AdminUser ou Clerk org séparée).
- Ne jamais mélanger les deux.

## Contenu
- Source de vérité : base Neon, éditée au back-office.
- L'app consomme un snapshot figé (`ContentRelease`), jamais le contenu live.
- Snapshot v1 embarqué dans le binaire. MAJ via `GET /content/latest` + swap SQLite au redémarrage.
- i18n : FR = langue originale. Carte sans `CardTranslation` → fallback FR.

## Modèle joueur
- 1 compte → N profils. Badges sur le compte. tagScores (archétype) sur le profil.
- Leaderboard = classement des profils DU compte (privé), pas mondial.
- Création de compte → merge local → cloud, idempotent (clientSessionId, localId).

## Freemium (préparé, pas construit en V1)
- Aucun paiement en V1. `EntitlementService` renvoie toujours true.
- Champs `tier` (free|premium) sur Category et par intensité, déjà en base.
- Le jour venu : abonnement via RevenueCat, webhook → `Account.premiumUntil`.

## Analytics
- PostHog Cloud EU. Opt-in explicite à l'onboarding. Aucune donnée perso.
- Stats propres (likes, cartes perso, comptes) : cron Vercel horaire → tables DailyStat/HourlyStat.

## Direction visuelle
- Fond sombre en base partout (pas gris neutre, noir teinté indigo). Mode clair en option (F2), jamais le défaut.
- Chaque jeu garde son dégradé `colorMain`→`colorSecondary` comme accent, contenu à sa tuile/son écran — jamais en fond d'app.
- Tuiles interactives : scale + glow coloré au tap/focus, jamais un aplat gris plat.
- Transition `Hero` (Flutter) réservée aux moments à fort enjeu : home→jeu, fin de partie. Pas sur chaque navigation.
- Détail complet : `docs/playlink-mobile-blueprint.html` §10.

## Conventions
- UI et contenu en FR + EN. Code et commentaires : suivre l'existant.
- Commentaires : seulement si le POURQUOI est non-évident.
- Chaque phase du plan de prototype = une PR revue avant la suivante.
- Migration : conserver les `id` cuid de l'ancienne base.
